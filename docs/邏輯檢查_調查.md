# CBS 邏輯檢查調查

## 1. 進入點

舊 CLI 的形式是 `python main.py --check <報單號> [<報單號> ...] [--save]`。它逐張呼叫 `txtrans.logiccheck.run_check(sersno, msgcode="5203S", save=..., progress=None, include_items=True)`。舊 CLI 預設只查，函式本身的 `save` 預設值則是 True，呼叫端須明確傳入。回傳 `CheckResult`，包括錯誤清單、規則執行數、整體與兩階段通過狀態、致命錯誤及是否寫入。進度回呼可省略。

## 2. 模組依賴

本機複製 `txtrans/__init__.py`、`logiccheck.py`、`custom_functions.py`、`context.py`、`models.py`、`utils.py`、`netcompat.py`、`notifier.py`、`db.py`、`config.py`、`mysql_compat.py`、`exchange.py`，以及 `expressions` 的 `__init__.py`、`calculate.py`、`logic.py`、`functions.py`、`validators.py`。SQLite 另沿用舊測試的 `sqlite_backend.py`。MySQL 使用 PyMySQL，SQLite 使用標準庫。執行入口由本機連線適配層提供資料庫映射，`get_config` 由適配層提供。依賴範圍限於上述模組。

## 3. 資料庫讀取

| 資料庫 | 已確認的讀取 |
| --- | --- |
| `cbssetcontent` | `tb_setifform`、`cbsFormType`、`cbsfielddata`、`tb_setifvar`。第 1 階段讀 `tb_setiftype`、`tb_setiftype_client`，第 2 階段讀 `tb_setiftype_item`。規則樹讀 `tb_setiflayer` 及其 `_client`、`_item` 版本。 |
| `cbsdata4` 對應的報單庫 | 明確讀取 `CUSDEC`、`INVITEM`、`CONTAINERNO`；其餘依 `cbsFormType` 指定的表與規則的欄位參照。可含 `CUSDEC_OTHER`、`CUSREP`、`CUSCAR`、`GOODSCHECK`、`CUSMCGD`、`CUSADFD` 及子表。部分總量函式會查 `SUMEXP`、`SUMSTC`、`SUMCTN`。 |
| `code4` 對應的代碼庫 | `mydeclarerate` 及規則指向的其他代碼表，並列舉資料表以解決欄位參照。 |
| 其他 | 共用運算式引擎另提供舊 EDI 日序與公共資料參數功能。日序函式有寫入能力，本外掛停用。公共資料若要用，須明確映射到測試 `xmlset` 庫的 `Cusparameters`；其餘未映射的庫直接拒絕。 |

## 4. 資料庫寫入

| 位置 | 寫入 |
| --- | --- |
| 規則庫 `TB_ErrorMsg` | 按 `PType`、`SerSno` 刪除同張舊結果。基本及客戶規則使用 `PLOGICTYPE < 2`，新資料寫 1。項次規則使用 `PLOGICTYPE = 2`，新資料寫 2。插入欄位為 `PType`、`PField`、`PFormCode`、`PErrorMsg`、`PgridIndex`、`SerSno`、`PRow`、`POtherCode`、`POtherField`、`PCheckMemo`、`PLOGICTYPE`。 |
| 報單庫 `CUSDEC`（本接口只用 5203S） | 把現有 `STATUS` 備份到 `原狀態`，更新 `STATUS`、`是否已邏輯`。通過時原狀態 0 轉 Y，其他原狀態保留，`是否已邏輯` 設 1。失敗時 `STATUS` 設 0，`是否已邏輯` 設 0。舊引擎也支援其他訊息類別，5135／5205 寫 `CUSREP` 的相同三欄。 |

舊 `run_check` 先分兩階段更新錯誤清單，再用合併結果更新主檔一次。舊資料庫層單筆自動提交，共用引擎另有日序寫入與 SQL 函式。本機入口限制寫入來源與表，只有 `--save` 可寫。每張報單的結果在同一交易中提交，致命錯誤則回滾。

## 5. 無法運算與無規則

`LogicChecker._check_table` 對運算失敗、規則執行例外或明細表查詢失敗，記為 `engine=True` 並使整張不通過。讀取必要規則表失敗或沒有基本規則對應則為 `fatal`。項次未設定特殊規則時，舊引擎會做項次資料完整性檢查。另有一個邊界情形，已對應的規則若沒有可建立的節點，舊迴圈會跳過，沒有增加規則數，也沒有記成引擎錯誤。本機外掛在載入規則樹時標記這個情形，避免它被誤報成通過。

## 6. Python

外掛入口與所列舊模組使用 Python 3.7 相容語法。MySQL 若指定 Python 3.7，需使用仍支援該版本的 PyMySQL；SQLite 路徑不需要 PyMySQL。fuelcore 仍使用自己的 Python 版本要求，兩者由子程序隔離。

## 本機資料現況

指定的送收信搬移包包含 XML 設定與回信結構，列印搬移包包含報表範本。正式 F6 驗收需要另外提供 `cbssetcontent` 規則表匯出與對應假報單日期的 `code4.mydeclarerate`，以及規則實際參照的其他代碼表。測試需同時設定 `FUELCORE_LOGIC_PLUGIN` 與指向該測試資料的 `FUELCORE_CBS_CONFIG`。

## 實作與驗收補記

- `python -m pytest -q` 通過 76 項、跳過 1 項、失敗 0 項。跳過的是需要正式規則及匯率 CSV 的測試。工作台驗收使用獨立 Tk 子程序。
- 18 個舊檔逐檔 SHA-256 比對一致。另新增本機 `run_check.py` 和 `check_db.py`，提供 JSON 入口、唯讀連線、錯誤遮蔽與測試庫交易限制。外掛程式在 repo 外。Git 只包含 fuelcore 介面、操作說明與自製測試外掛。
- SQLite 本機驗證使用轉檔核心產生的四張假報單及合成規則。一張通過，三張失敗，欄位分別為數量、報單品名、DUTYAMT。唯讀前後資料庫檔一致。移除已對應的規則節點會記為無法檢查。
- `--save` 實測把通過的 `CUSDEC.STATUS` 由 0 更新為 Y，`是否已邏輯` 變成 1，`原狀態` 記為 0。失敗報單的狀態與旗標為 0，並在 `TB_ErrorMsg` 寫入 `PLOGICTYPE` 1 或 2。模擬主檔寫入失敗時，錯誤清單與主檔變更一併回滾。
- 送信模擬只讀既有狀態。工作台執行唯讀檢查，結果在這次工作台執行期間顯示。封裝版須指定獨立 Python 執行檔。
- MySQL 路徑將報單、代碼與規則映射到各自的測試庫，寫入表要求 InnoDB。預設查詢使用唯讀交易，SQL 函式限制為已知的讀取用途。應使用獨立測試帳號和無外部寫入觸發器的測試庫。真實 MySQL 版本、規則 SQL 相容性及 CBS F6 結果仍須用測試庫比對。
- 以 Python 3.7 語法模式驗證外掛所有檔案，實際執行環境為 Python 3.12。正式整合測試使用有表頭的 UTF-8 CSV。假報單使用 115 年 10 月下旬 USD，轉檔後匯率為 31.43800。
